# ADR-007: 限流狀態必須放在實例之外

狀態：已採納

## 背景

Stage 2 到 Stage 4 的限流狀態存在 `ConcurrentHashMap` 裡，也就是**單一 JVM 的記憶體**。
`@Component` 是 singleton，但 singleton 的範圍是「每個 ApplicationContext 一個」——
起兩個實例就是兩份完全獨立、互不知情的狀態。

Stage 4 實測（`capacity = 20`，60 個請求輪流打兩個實例）：

```
通過 40 次，擋掉 20 次
```

每個實例各收到 30 個請求，各自放行自己那 20 個。
**實際上限 = 設定值 × 實例數。**

失效的方向特別糟：實例越多，限制越鬆。k8s 在高負載時自動擴容，
限流上限會跟著放寬 —— 正好在最需要保護的時候保護最弱。

## 決定

把限流狀態移到 Redis，用 Lua 腳本保證「讀取 → 計算補充 → 扣減 → 寫回」的原子性。

## 理由

評估過三條不需要外部儲存的替代路線，都比「把狀態放到共用的地方」麻煩：

| 做法 | 代價 |
|---|---|
| 配額除以實例數（20 / 2 = 每實例 10） | 實例數變動就要重算；流量不均勻時會誤殺還有額度的那一邊；自動擴縮容下根本算不準 |
| 實例之間用 gossip 同步計數 | 有傳播延遲（延遲期間仍然超發）、網路成本、實作複雜度遠高於接一個 Redis |
| 一致性雜湊把同一個 key 固定路由到同一個實例 | 需要 gateway 配合；實例掛掉或擴縮容時 key 會重新分配，狀態跟著消失 |

共通點是：它們都在迴避「共用狀態」這件事，結果是把複雜度搬到別的地方，而不是消除它。

Redis 另外解決了一個既有問題：`ConcurrentHashMap` 只增不減，
每個出現過的 client key 都永久留著（被掃描器打時會累積大量條目）。
Redis 的 TTL 讓過期的 key 自動消失，不需要自己寫清理排程。

## 取捨

- **多一個必須存活的元件。** Redis 掛掉時限流器要怎麼辦，是一個必須明確回答的新問題
  —— fail-open（放行，可能被打爆）或 fail-closed（全擋，自己造成故障）
- **每個請求多一次網路往返。** 本機記憶體是奈秒級，Redis 是毫秒級
- **時間基準要改用 Redis 的 `TIME`**，不能用各實例的 `System.currentTimeMillis()`
  —— 多台機器時鐘不同步會讓補充計算產生偏差
- 原子性從「JVM 內的 CAS」換成「Redis 單執行緒執行 Lua」，
  是同一個問題換一個層次解決，不是消失了

## 後續

Stage 5 完成後，用同一組指令重跑 Stage 4 的實驗，**通過次數必須回到 20**。
那個數字是這個決定是否成立的唯一驗收標準。

fail-open / fail-closed 的選擇留到 Stage 5 實作時再決定，屆時應另立一份 ADR。
